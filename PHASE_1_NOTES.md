# Phase 1 Notes — DeepCamera Foundation & Calibration

## What was built

1. **`skills/detection/floorwatch-coverage/`** — new skill package, structured like the reference `yolo-detection-2026` skill (`SKILL.md`, `config.yaml`, `deploy.sh`/`deploy.bat`, `requirements.txt`, `scripts/`, `tests/`). It is a **downstream consumer**, not a frame-consuming detection skill: it reads `detections` JSONL events (the same shape `yolo-detection-2026` emits) from stdin, maps each `person` bounding box into calibrated zone polygons, and emits raw `zone_presence` events. No ML/GPU dependencies — pure-Python geometry (ray-casting point-in-polygon), stdlib only.
2. **`skills.json`** — registered `floorwatch-coverage`, `status: "experimental"`, with a `depends_on: ["yolo-detection-2026"]` field (not part of the existing schema for other entries — flagging in case the registry loader validates against a fixed field set).
3. **Zone-calibration tool** — `skills/detection/floorwatch-coverage/calibration/`: a framework-free HTML5 canvas page (`index.html`) + a stdlib-only Python HTTP server (`calibration_server.py`, no Flask/etc.). Operator drops a still frame into `calibration/frames/<camera_id>.jpg`, draws polygons by clicking, and saves to `zones/<camera_id>.json` — verified end-to-end in-browser (draw → save → file written with correct schema).
4. **Zone-mapping logic** (`scripts/main.py`, `scripts/zone_utils.py`) — unit tested (`tests/test_main.py`, 10 passing tests): confidence filtering, bbox→anchor-point reduction (`bottom_center` default, approximating foot position), point-in-polygon, per-zone `occupied`/`entity_refs` aggregation. A person is assigned to at most one zone (first polygon match).
5. **End-to-end smoke test** (`tests/run_pipeline_test.py`) — proves the required data path (camera → detection → Floorwatch skill → console log) by spawning the upstream detector and `floorwatch-coverage/scripts/main.py` as real subprocesses communicating over the actual JSONL protocol, feeding 9 simulated frames, and asserting both `occupied` and `gap` presence events come out correctly zone-mapped. **Run it**: `python skills/detection/floorwatch-coverage/tests/run_pipeline_test.py`.

## Deviations from the brief — flagged explicitly, not silently worked around

- **No real cineplex cameras or RTSP feeds available in this environment.** Per Phase 1's own allowance, the smoke test uses a single static test image (`docker/od/panda.jpg`, already in the repo) standing in for a camera capture, fed as repeated frames. This proves the wiring, not real-world detection accuracy on live video.
- **No internet access in this dev sandbox** — `pip install ultralytics torch` (required by the real `yolo-detection-2026` skill) could not be run, so I could not execute the actual YOLO26 model here. To still prove the pipeline honestly rather than fake success:
  - Built `tests/stub_upstream_detector.py` — a detector double that speaks the **identical** JSONL protocol (`ready`/`frame`/`detections`/`stop`) as `detect.py`, but returns deterministic, clearly-labeled synthetic bounding boxes (its own docstring says so, and it emits a `note` field flagging itself as synthetic in its `ready` event).
  - `run_pipeline_test.py` auto-detects whether `ultralytics` is importable: if yes, it drives the **real** `yolo-detection-2026/scripts/detect.py`; if no, it falls back to the stub and prints which mode ran. `floorwatch-coverage/scripts/main.py` is exercised unmodified either way — only the upstream is swapped.
  - **Before Phase 2**, please confirm this can run in an environment with internet access (or a pre-downloaded model cache) so the real YOLO26 model is validated against the actual pipeline, not just the stub.
- **No existing Floorwatch dashboard prototype was found in this repository.** The brief states one already exists ("floor status grid, event feed, supervisor queue, task effort cards"). A repo-wide search turned up nothing under any related name. Phase 2 explicitly requires reusing that prototype's rendering functions and swapping only its event source — **I need those prototype file(s) from you before Phase 2 can start for real**, otherwise Phase 2 would have to build a dashboard from scratch, which contradicts the brief's intent.
- Zone polygons are calibrated in the coordinate space of whatever still frame is used for calibration. This only stays correct if that still is captured at the **same resolution** as the live feed the detection skill actually receives — flagged prominently in both `SKILL.md` and the calibration tool's UI copy, but worth a manual sanity check once real cameras are wired up.
