# Phase 4 Notes — Real Trial & Review

## What was built

1. **`tools/accuracy_audit/`** — sampling harness stratifying logged events by (camera_id, hour-of-day bucket) as a proxy for "different times of day/lighting/camera angles" (flagged as a proxy, not real lighting metadata — see its README), plus `compute_accuracy.py` turning a human-reviewed sample into a false-positive-rate report. 11 tests. Verified with a real manual walkthrough (synthetic digest → sample → simulate human review → compute accuracy → feed into the checklist), not just unit tests.
2. **`services/floorwatch-rules-engine/tests/test_simulated_shift.py`** — unattended end-to-end test chaining the *real* `floorwatch-coverage` and `floorwatch-pose` subprocesses, a real Redis Stream, and the real FastAPI rules engine through a 20-frame simulated shift. Asserts zero unhandled errors (scans subprocess stderr for tracebacks) and zero dropped events (`XPENDING` == 0 on both consumer groups — every published event was consumed and acked).
3. **`app/notifications.py`** — real Twilio SMS and Firebase Cloud Messaging sender integrations, gated by `FLOORWATCH_NOTIFY_CHANNEL` and *always* short-circuited by `FLOORWATCH_SHADOW_MODE` (flipping shadow mode back on instantly stops all real sends regardless of channel config, per the brief). 13 unit tests against mocked SDK clients, plus two safety-property tests in `test_engine.py` proving shadow mode literally never calls the notifier.
4. **`go_live_checklist.py`** — a real, executable CLI gate (not documentation) checking: reviewed false-positive rate below target, roster cross-check active, contact directory populated for every staffed zone, and a live-tested notification channel (Twilio credential fetch / FCM credential load — never sends a real message). Exits non-zero on any failure. 18 unit tests on individual checks plus 2 tests running the actual `main()` entrypoint end-to-end (one passing, one correctly failing).
5. **`shift_digest_job.py`** — end-of-shift summarization: total events, breakdown by event type/zone, and recurring-vs-one-off pattern tagging per (zone, hour-bucket) based on whether that combination has been seen on ≥2 distinct calendar dates. Plain script (not a Celery task — see rationale in its docstring) meant for cron/Task Scheduler/Celery Beat. Writes both JSON and Markdown. 12 tests.
6. **`test_go_live_flow.py`** — chains all of the above: runs the actual checklist CLI to a genuine exit-0, runs a live-mode (`shadow_mode=False`) shift that fires a real (mocked-SDK) Twilio call for a legitimate gap while proving a gap in an unstaffed zone produces zero escalation (only an audit-log entry), then runs the shift-digest job against the resulting real digest file.

**102 tests pass** across the whole Floorwatch codebase after this phase (66 from Phases 1–3 + 36 new).

## A real bug this phase's testing caught

While building the simulated-shift test, my first WebSocket-collection design used a persistent background thread reading `receive_json()` in a loop, closed from the main thread — this **deadlocked** the test process repeatedly (confirmed by isolating with minimal diagnostic scripts and hard OS-level timeouts). Root cause: Starlette's TestClient WebSocket test session isn't safe for a blocking `receive()` call on one thread while another thread closes the connection. Fixed by never sharing a long-lived reader thread — each collection attempt gets its own throwaway daemon thread with a bounded `join()`, and any attempt that doesn't return in time is simply abandoned rather than waited on. Also added `pytest-timeout` (`pytest.ini` sets a 60s default) to this service's test suite going forward, so a hang like this fails loudly instead of consuming unbounded time.

## Deviations from the brief — flagged explicitly

- **No real Twilio account or Firebase project exists in this dev sandbox.** `notifications.py`'s send paths are real, production integration code, but have only been exercised against mocked SDK clients — never Twilio's or Firebase's actual APIs. `go_live_checklist.py`'s notification check will correctly and honestly report `[FAIL]` until real credentials are supplied — I ran it for real against a genuine (synthetic-but-real-format) accuracy report and confirmed exactly that: 3 of 4 checks pass, the notification check fails for the right reason. **This is the one thing that cannot be verified further without you providing real credentials.**
- **Contacts are placeholder phone numbers** (`contacts.json`, matching `roster.json`'s manually-maintained pilot pattern) — replace with real employee/supervisor numbers or FCM tokens before any real go-live.
- **The shift-digest job is a plain script, not a Celery task**, even though this repo has existing Celery infrastructure (`docker/`, `src/face_detection/celeryconfig.py`) — no broker is actually running in this sandbox (the Redis used throughout this phase is `fakeredis`, not the real service), so standing up unused Celery scaffolding felt like the wrong tradeoff. The summarization logic is a plain function (`summarize()`) that would wrap trivially in a `@app.task` if/when you want real Celery Beat scheduling.
- **Recurring-vs-one-off pattern tagging uses the same hour-of-day-bucket proxy** as the accuracy-audit harness (no separate "lighting" or "day-of-week" dimension) — flagged in the same place, same caveat.
- **The accuracy-audit "ground truth" used in the real manual walkthrough was simulated** (fabricated TP/FP labels with a fixed random seed and 8% FP injection rate), because no real shift history exists here. The harness itself is real and tested; what it needs to actually validate accuracy is real shift data with a human filling in `ground_truth` from what they actually observed.

## Addendum — Per-employee notification channel (SMS vs. FCM)

Built per your request. Important scoping note first: this service has **two separate, non-integrated notification/contact systems** — `contacts.json`/`ContactBook` (this phase's original work, above: zone-keyed, no employee identity, feeds Part A/B's anonymous Tier 1/2 nudges) and `employee_directory`/`floorwatch_employees` (built later, in `PHASE_3_NOTES.md`'s addendum: per-person identity, feeds the task-assignment SMS workflow). Per-employee channel routing only makes sense on the latter — `contacts.json` has no per-person record to hang a channel preference on — so **this change applies to `employee_directory` only; `contacts.json`/`ContactBook`/the global `NOTIFY_CHANNEL` sender built in `main.py` are untouched.**

- Added `channel` (`"sms" | "fcm"`, nullable) and `fcm_token` fields to `employee_directory` records, validated at write time (`validate_channel()` — unset/empty is valid and means "use the deployment default"; anything else must be exactly `"sms"` or `"fcm"`). Existing Postgres deployments get these columns via `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (not folded into the `CREATE TABLE IF NOT EXISTS`, which wouldn't touch an already-existing table).
- `main.py` now builds **both** a Twilio and an FCM sender unconditionally at startup (`TASK_CHANNEL_SENDERS`), independent of the global `NOTIFY_CHANNEL` toggle — an employee's own `channel` field can select either regardless of the deployment default. `build_sender()`'s existing never-raises/falls-back-to-NoOpSender behavior covers a channel that isn't actually configured.
- `_send_task_notification()` resolves each employee's effective channel (their own `channel` field, or `DEFAULT_TASK_CHANNEL` — derived from the deployment's existing `NOTIFY_CHANNEL` so every employee added before this feature keeps behaving exactly as before, per your explicit backward-compatibility requirement) and routes to the matching sender.
- **Explicitly does not guess a fallback channel.** An employee configured for `fcm` with no `fcm_token` on file gets a clear "no fcm token on file" skip and a warning log — never a silent retry over SMS (which could reach a stale or wrong number), and vice versa. Verified in `tests/test_reassignment.py`'s channel-routing tests, including one proving the *other* channel's sender is never even called.
- **A pre-existing gap this fixes rather than introduces:** before this change, `_send_task_notification()` always built its `to_context` as `{"phone": phone}` regardless of the configured channel — meaning a deployment with `FLOORWATCH_NOTIFY_CHANNEL=fcm` would have had every task-assignment notification silently fail forever (`FcmSender.send()` reads `to_context["fcm_token"]`, which was never populated). That path is exercised correctly now.
