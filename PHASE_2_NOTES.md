# Phase 2 Notes — Part B: Coverage Engine

## What was built

1. **`skills/detection/floorwatch-coverage/`** extended from Phase 1's raw per-frame presence to schema-compliant output: `scripts/debounce.py` (`ZoneDebouncer`/`DebouncerRegistry`) turns noisy frame-by-frame occupancy into stable `zone_covered`/`zone_gap` transitions — 60s debounce, ≥0.8 confidence threshold before a gap fires, per the brief. Every emitted event is validated against `skills/lib/floorwatch_schema.py` (new — the one shared Pydantic schema, extended with optional Phase 2 fields rather than forked) before being written; malformed events are rejected and logged, never passed downstream. Optionally publishes onto a Redis Stream (`--redis-url`).
2. **Redis Streams event bus** — confirmed with `tests/test_redis_publish.py`: the skill's `redis`-client publisher (unmodified production code) delivers events readable by an independent consumer via `XRANGE`.
3. **`services/floorwatch-rules-engine/`** — new standalone Python/FastAPI service (per your choice of stack) implementing the Tier 1→2→3 escalation state machine (`app/engine.py`, 19 passing unit/integration tests): nudge timer + shift cap + bypass, supervisor-command timer + hourly throttle, Tier 3 → shift-digest log, 15-min per-zone resolve cooldown, roster cross-check as a hard precondition before any nudge, shadow-mode suppression of real sends, and REST endpoints (`/api/queue/zone/{id}/approve|reassign`) so a human explicitly approves every Tier 2 directive — nothing auto-sends.
4. **`dashboard/floorwatch_demo.html`** rewired per your docx's Section 3 spec: the `script[]`/`run()` simulator is gone, replaced by a `WebSocket` connection + `applyEvent()` reading real events, with automatic reconnect and REST rehydration (`/api/state`, `/api/queue`) on load. `renderZones`, `renderQueue`, `renderTasks` are structurally unchanged, as intended.
5. **Verified live, not just in tests**: ran the real coverage skill's debounce logic, a fake-but-protocol-real Redis (see below), the actual FastAPI rules engine, and the actual dashboard HTML in a browser together — watched a published `zone_gap` flow through to a "Nudge sent" state on the floor grid, escalate for real (180s wall-clock nudge timer genuinely expired mid-session) to a drafted supervisor command in the queue, and resolved it via the dashboard's Approve button hitting the real REST endpoint. This live run caught a real bug (see below), not just a scripted demo.

## Bug found and fixed during live verification

`RulesEngine.approve()` rejected zones already at Tier 3 (`escalated`), so once a zone auto-escalated, the dashboard's Approve/Reassign buttons for it silently 404'd — a supervisor would have no way to close out an escalated zone from the UI. Fixed to accept `escalated` in both `approve()` and `pending_commands()` (so the queue keeps showing it), with regression tests added (`test_approve_still_works_after_tier3_escalation`, `test_pending_commands_includes_escalated_zones`).

## Deviations from the brief — flagged explicitly

- **Nudge caps and command throttling are scoped per-zone, not per-employee/per-supervisor.** The brief says "cap 3 nudges/employee/shift" and "throttle 5/supervisor/hour," but Phase 1/2 detections only carry per-frame anonymous `entity_ref`s (e.g. `track_0`), not identity stable across frames — there's no persistent "this employee" or "this supervisor" to key a cap on yet. Real re-ID is called out as Phase 3+ scope in `PHASE_1_NOTES.md`. Documented in `engine.py`'s module docstring so this isn't silently wrong later.
- **No real Redis instance in this sandbox.** Docker Desktop is installed but wouldn't come up headlessly here (needs interactive setup). All Redis-dependent tests and the live demo used `fakeredis.TcpFakeServer` — a real TCP server speaking the actual Redis protocol — with the exact same `redis`-client production code on both the publisher (coverage skill) and consumer (rules engine) sides. **Before real deployment, please confirm this runs against the actual `redis` service already in `docker/docker-compose.yml`** — I'd expect it to work unmodified (it's the same client, same protocol), but it hasn't been checked against a real Redis server.
- **Roster is a static `roster.json` file**, matching the brief's "a manually maintained list is fine for pilot" — but it's currently one flat `zone_id -> bool`, with no per-shift or per-time-window granularity. Fine for a pilot; will need real shift data before go-live per the brief's Section 7.
- **Notification channel is not wired.** Shadow mode (`FLOORWATCH_SHADOW_MODE=true`, default) suppresses every real send — nudges and supervisor directives are computed, logged, and broadcast to the dashboard, but nothing reaches a real employee device or SMS/push channel yet. That's explicitly Phase 4 scope (Firebase/Twilio) per the brief.
- **`zones_meta.json`'s role_tag mapping is approximate** — the dashboard's original zone list has "Customer Service" (lobby) and "Security" (entrance) as free-text roles; the shared schema's `role_tag` enum only allows `concession | usher | janitor | maintenance | ticketing | security`, so I mapped lobby→`usher` and entrance→`security` as closest fits. Worth confirming these are the right categories for your actual zone list before go-live.
